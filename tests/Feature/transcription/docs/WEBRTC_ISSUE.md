# ISSUE: WebRTC Signaling Handshake Failure (400 Bad Request)

## Context
We are implementing OpenAI Realtime API via WebRTC.
The backend signaling controller (`RealtimeSignalingController.php`) is implemented and verified to connect to OpenAI's `/v1/realtime` endpoint successfully via `tinker`.

## The Problem
When clicking "Aufnahme starten" in the browser, the frontend sends a `POST` request to `/req/transcription/realtime/signaling`. 
OpenAI returns a `400 Bad Request` with the error:
`Failed to parse offer: failed to unmarshal SDP: EOF` (or similar SDP parsing errors).

## Current State
- **Database**: `api_format_endpoints` has `realtime.signaling` -> `/realtime`.
- **Backend**: `RealtimeSignalingController` is using `gpt-4o-realtime-preview-2024-12-17`.
- **Frontend**: `realtime_transcription.js` and `LiveTranscriptionManager.js` are handling the WebRTC flow.
- **Verification**: `tinker` probes show that OpenAI returns a valid `Location` header when sent a (dummy) SDP, but the browser's real SDP is causing a 400.

## Suspected Causes
1. **SDP Formatting**: The SDP generated by the browser might be missing required fields or headers (e.g., `v=0`) when it reachers OpenAI through the PHP proxy.
2. **Body Encoding**: The PHP `Http` client might be mangling the raw SDP string (which must be sent as `application/sdp` or `text/plain` depending on the gateway).
3. **Model Sync**: Even though `tinker` sees the new model, the running FPM process might still have cached config (though `cache:clear` was run).

## Task for Next Agent
1. **Debug the exact payload**: Use `Log::debug` in `RealtimeSignalingController` to capture the EXACT string being sent to OpenAI from a real browser request.
2. **Compare with OpenAI Docs**: Ensure the SDP body matches the expectations for the `v1/realtime` REST signaling endpoint.
3. **Fix the Proxy Logic**: Ensure the raw body from the frontend is passed bit-for-bit to OpenAI without any Laravel/Guzzle transformation.
